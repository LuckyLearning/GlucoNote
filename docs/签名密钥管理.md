# 签名密钥管理

本文说明 GlucoNote 的 Android 签名密钥：**怎么生成、怎么备份、怎么配到 CI、丢了怎么办**。

> 密钥本体、口令、导出文件全部在 `.toolchain/keystore/`，该目录已在 `.gitignore` 中忽略，**绝不入库**。

---

## 1. 当前密钥信息

| 项 | 值 |
|---|---|
| 文件 | `.toolchain/keystore/gluconote.jks` |
| 类型 | JKS |
| 别名（alias） | `gluconote` |
| 算法 | RSA 2048 |
| 有效期 | 10950 天（约 30 年） |
| 证书 SHA-256 指纹 | `95:BC:40:79:0D:D4:D6:E1:5E:EF:3A:BF:FD:A1:DA:F2:60:BC:41:E7:B8:46:00:DE:E7:E0:06:88:32:8D:A9:34` |
| DN | `CN=GlucoNote, OU=LuckyLearning, O=LuckyLearning, L=Unknown, ST=Unknown, C=CN` |

口令保存在同目录的 `keystore.properties`（`STORE_PASSWORD=…`），keystore 与 key 使用同一口令。

> ⚠️ **这是 GlucoNote 专属密钥，不要复用 WindTone 的密钥**。两个应用各自独立签名，混用会导致更新安装被系统拒绝。

## 2. 重新生成（仅在丢失时）

```bash
export JAVA_HOME=/c/Users/stu_l/.jdks/openjdk-21.0.2
cd C:/esendev/code/temp/GlucoNote
mkdir -p .toolchain/keystore

# 1. 生成随机口令
PW=$(head -c 18 /dev/urandom | base64 | tr -d '/+=' | head -c 20)
echo "STORE_PASSWORD=$PW" > .toolchain/keystore/keystore.properties

# 2. 生成 keystore
"$JAVA_HOME/bin/keytool" -genkeypair -v \
  -keystore .toolchain/keystore/gluconote.jks -storetype JKS \
  -alias gluconote -keyalg RSA -keysize 2048 -validity 10950 \
  -storepass "$PW" -keypass "$PW" \
  -dname "CN=GlucoNote, OU=LuckyLearning, O=LuckyLearning, L=Unknown, ST=Unknown, C=CN"

# 3. 验证
"$JAVA_HOME/bin/keytool" -list -keystore .toolchain/keystore/gluconote.jks -storepass "$PW"

# 4. 导出给 CI 用的 Base64 文件
base64 -w0 .toolchain/keystore/gluconote.jks > .toolchain/keystore/gluconote.jks.base64
```

> `-storetype JKS` 是刻意的：PKCS12 在新版 keytool 下生成的密钥库，老版本 OpenJDK 读取时可能报 `Tag number over 30 is not supported`（ASN.1 标签不被支持）。JKS 兼容性最广。

## 3. 备份清单（务必离线保存）

签名密钥一旦丢失，**已发布的用户将无法通过应用内更新升级**（系统会视为不同应用、拒绝覆盖安装），只能让用户卸载重装且数据丢失。

请把这 4 项一起存进密码管理器 / 离线介质：

- [ ] `gluconote.jks` 文件本体
- [ ] `STORE_PASSWORD`（即 `keystore.properties` 里的值）
- [ ] 别名 `gluconote`
- [ ] 证书 SHA-256 指纹（用于核对）

> 建议同时把 `gluconote.jks.base64` 存一份 —— 恢复 CI 时可以直接粘贴，不必重新编码。

## 4. 配到 GitHub Secrets

打开 **GlucoNote 仓库 → Settings → Secrets and variables → Actions → New repository secret**，逐个添加：

| Secret 名称 | 值从哪来 |
|---|---|
| `KEYSTORE_BASE64` | `.toolchain/keystore/gluconote.jks.base64` 的**全文**（约 3000 字符，一行） |
| `KEYSTORE_PASSWORD` | `keystore.properties` 里的 `STORE_PASSWORD` |
| `KEY_ALIAS` | `gluconote` |
| `KEY_PASSWORD` | 与 `KEYSTORE_PASSWORD` 相同 |
| `RELEASE_TOKEN` | 对 `LuckyLearning/Release` 有写权限的 PAT |

查看待粘贴的值：

```bash
cd C:/esendev/code/temp/GlucoNote
cat .toolchain/keystore/keystore.properties
cat .toolchain/keystore/gluconote.jks.base64
```

> **`KEYSTORE_BASE64` 必须是完整的一行**。从文件复制时若在中间折行或截断，CI 会解出损坏的密钥库（表现为 `Failed to read key … Tag number over 30 is not supported`）。工作流里已加了字节数与 `keytool -list` 双重校验来提前暴露这个问题。

## 5. CI 侧的防护（已实现）

`.github/workflows/build-release.yml` 的 `release` job 在真正构建前有三道检查：

| 步骤 | 作用 | 失败提示 |
|---|---|---|
| `Check signing secrets` | 四个 Secret 任一为空即失败 | `缺少签名相关的 Secrets: KEYSTORE_BASE64 …` |
| `Decode signing keystore` | 校验解码后字节数 | `解码出的 keystore 只有 N 字节，KEYSTORE_BASE64 可能不完整或为空` |
| `Verify keystore is readable` | `keytool -list -alias` 独立验证 | `keytool 无法读取该 keystore —— 请确认三者匹配` |

**为什么需要这三道**：不加的话，空 Secret 会一路走到 `packageRelease`，报出 `Failed to read key  from store "...": Tag number over 30 is not supported` —— 错误信息里 key 名是空的、原因指向 ASN.1 解析，完全看不出是"Secret 没配"。

---

## 6. 常见问题

| 现象 | 根因 | 处理 |
|---|---|---|
| `Failed to read key  from store …`（key 名为空） | `KEY_ALIAS` 为空 | 重新配置 `KEY_ALIAS` = `gluconote` |
| `Tag number over 30 is not supported` | `KEYSTORE_BASE64` 不完整/为空，或密钥库是新版 PKCS12 | 用 `-storetype JKS` 重新生成；核对 base64 长度 |
| `Keystore was tampered with, or password was incorrect` | 口令不对 | 核对 `KEYSTORE_PASSWORD` |
| `keytool error: java.io.IOException: keystore password was incorrect` | 同上 | 同上 |
| 安装时提示「应用未安装 / 签名不一致」 | 与已装版本的签名不同 | 只能卸载重装（数据会丢）；**因此密钥必须从一开始就固定并备份** |
| 更新后系统提示降级 | `versionCode` 变小 | 见 `版本与更新.md` §2，code 只能递增 |

## 7. 验签（发布后核对来源）

从公共仓库下载 APK 后，比对签名证书指纹：

```bash
# 提取 APK 签名信息（需 build-tools 里的 apksigner）
"$ANDROID_HOME/build-tools/34.0.0/apksigner" verify --print-certs dist/GlucoNote-v1.0.0.apk

# 输出中的 SHA-256 digest 应与第 1 节表格里的指纹一致
```
