# GlucoNote 数据层优化方案

> 版本：v1（2026-10-27）
> 适用范围：`app/src/main/java/com/gluconote/data/**`、`util/Csv.kt`、`util/StatsUtils.kt`、`ui/*ViewModel.kt`
> 前提约束：`minSdk 26`、`room 2.6.1`、无 Paging3、**构建必须 `--offline`（不引入新依赖）**、血糖数据属敏感健康数据（迁移不可丢数据）

---

## 1. 目标

| 目标 | 衡量方式 |
|------|---------|
| 大数量级导入可用 | 3 年 5040 条 CSV 导入 < 1s（实测批量 0.22s，逐条事务约 220s，见 §6.5） |
| 分页与范围查询不随数据量线性劣化 | 记录页首屏查询由全表扫描变为索引查找 |
| 写入不引发全表重算 | 新增/编辑/删除一条记录，首页与统计不再重建全量列表 |
| 数据可演进 | DB 版本升级走显式 Migration，schema 可追溯 |
| 零新依赖 | `dependencies {}` 不新增条目，离线构建仍通过 |

## 2. 现状盘点

### 2.1 存储结构

**Room / SQLite `gluconote.db`，`version = 1`，`exportSchema = false`，单表 `records`**

| 字段 | 类型 | 说明 | 实际占用 |
|------|------|------|---------|
| `id` | TEXT PK | UUID 字符串 | 36 B + 主键索引项 |
| `measureTime` | INTEGER | epoch 毫秒 | 8 B |
| `value` | REAL | mmol/L（Float 存入为 double） | 8 B |
| `period` | TEXT | 5 种标签 key | 5~9 B |
| `note` | TEXT | 备注，空值存 `""` | 0~N B |
| `createdAt` | INTEGER | 创建时间 | 8 B |

**索引：0 个**（除主键自带索引）。

**设置**：DataStore Preferences（`settings`），6 个键。`save()` 刻意不写 `theme_mode`，写入职责已分离，无需改动。

### 2.2 代码位置索引

| 关注点 | 位置 |
|--------|------|
| 表定义 | `data/model/GlucoseRecord.kt` |
| DB 定义 / 版本 | `data/local/AppDatabase.kt:7` |
| DB 构建（无 fallback） | `GlucoNoteApp.kt:14-21` |
| 查询 / 分页 SQL | `data/local/RecordDao.kt:13-77` |
| 批量写（400/块） | `data/repository/RecordRepository.kt:41-46` |
| CSV 导入（逐条写） | `ui/profile/ProfileViewModel.kt:104-108` |
| CSV 导出（全量读） | `ui/profile/ProfileViewModel.kt:102` |
| 记录页分页 + count 刷新 | `ui/records/RecordsViewModel.kt:48-62, 78-134` |
| 首页全量加载 | `ui/home/HomeViewModel.kt:33-53` |
| 统计全量加载 + 5 次聚合 | `ui/stats/StatsViewModel.kt:56-83` |
| 聚合算法（纯函数） | `util/StatsUtils.kt` |

### 2.3 当前读写路径

**读**
- 记录页：keyset 分页（`measureTime DESC, id DESC` + `LIMIT 25`），比 OFFSET 稳，**设计正确**。
- 首页 / 统计页：`repo.observeAll()` 一次拉全表。统计页再对全量列表跑 5 组聚合（trend / rate / buckets / range7 / range30）。

**写**
- 新增/编辑：`upsert` → 单条 insert 或 update。
- 删除：单条 delete，本地列表同步移除。
- 导入：`parseCsv()` 后 `list.forEach { repo.insert(it) }` ← **每条一次事务**。
- 导出：`repo.getAll()` 全量 → 内存拼字符串。

### 2.4 量级测算

| 场景 | 条数 | DB 估体积 | 当前架构表现 |
|------|------|----------|-------------|
| 3 年、5 次/天 | ~5,000 | ~0.5 MB | 可用，导入慢 |
| 10 年、5 次/天 | ~17,000 | ~1.7 MB | 统计页每次写入全量重算，可感 |
| 10 年、10 次/天（极端） | ~36,000 | ~3.6 MB | 明显卡顿风险 |

结论：**不是「存不下」问题，是「每次写都全表重算」和「导入无事务」问题。**

## 3. 问题清单

| ID | 问题 | 证据 | 影响 | 严重度 |
|----|------|------|------|--------|
| P0-1 | 导入逐条事务 | `ProfileViewModel.kt:106` `list.forEach { repo.insert(it) }`，`RecordDao.insert` 为单条 `@Insert` | **实测 981×** 差距：1000 条逐条 43.8s vs 批量 0.045s（见 §6.5） | 高 |
| P0-2 | 无任何二级索引 | `GlucoseRecord.kt` 无 `indices` | 客观实测：18k 行时旧查询 0.03–0.04 ms/次，**当前不是瓶颈**；价值在于防止数据量增长后的退化，且必须与迁移一起做（边际成本为零） | 中 |
| P1-1 | 编辑后列表不刷新 | `RecordsViewModel.kt:50-61` 仅监听 `observeCount()`；update 不改变行数 | 编辑一条后返回记录页仍是旧值，需切 Tab 重进才更新 | 高（正确性） |

| P1-3 | 同一份数据被反复遍历 | `StatsViewModel.kt:65-78`：filter 两次、5 个函数各自再 filter/map | 5000 条时约 6~8 次全量遍历，1.7 万条时倍数放大 | 中 |

| P2-1 | 无迁移策略与 schema 快照 | `AppDatabase.kt:7` `exportSchema = false`；`GlucoNoteApp.kt` 未配 fallback | 一旦升版本又没写 Migration，启动即崩；也没有 schema 可对照 | 高（前置阻断 P0-2） |

| P2-5 | 导出全量驻留内存 | `exportCsv(repo.getAll())` | 3.6 万条时峰值约几十 MB 字符串 | 低 |
| P2-6 | 趋势图逐点绘制 | `computeTrend` 返回每条记录一个点 | 近 1 年约 1800 点，Canvas 绘制与触摸都不划算 | 低（体验） |

## 4. 方案

分三阶段，**阶段一必须先做**（它是阶段二的前提：有了索引和 schema 才能安全动查询）。

### 阶段一：事务 + 索引 + 迁移（P0 / P2-1）

#### 1.1 导入走批量事务

`RecordDao` 与 `RecordRepository` 已有 `insertAll`（400/块）。只需把导入入口从「逐条」改成「一次批量」，并用 `room-ktx` 的 `withTransaction` 把整批包成一个事务（**room-ktx 已在依赖中，无需新增**）。

```kotlin
// data/repository/RecordRepository.kt
suspend fun insertAllInTransaction(records: List<GlucoseRecord>) = withContext(Dispatchers.IO) {
    db.withTransaction {           // androidx.room.withTransaction
        records.chunked(400).forEach { db.recordDao().insertAll(it) }
    }
}
```

```kotlin
// ui/profile/ProfileViewModel.kt
suspend fun importText(text: String): Int {
    val list = parseCsv(text)
    repo.insertAllInTransaction(list)   // 原：list.forEach { repo.insert(it) }
    return list.size
}
```

预期：5040 次事务 → **1 次事务（内部 13 个 INSERT 语句）**。此改动不涉及 schema，可单独发版。

#### 1.2 加索引 + DB 升到 v2

```kotlin
@Entity(
    tableName = "records",
    indices = [
        Index(value = ["measureTime", "id"], name = "index_records_measureTime_id"),
        Index(value = ["period", "measureTime", "id"], name = "index_records_period_measureTime_id")
    ]
)
data class GlucoseRecord(/* 字段不变 */)
```

```kotlin
// data/local/AppDatabase.kt
@Database(entities = [GlucoseRecord::class], version = 2, exportSchema = true)

val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        // 索引名必须与 Room 依据 @Index 生成的名称完全一致，否则启动时 schema 校验失败
        db.execSQL("CREATE INDEX IF NOT EXISTS `index_records_measureTime_id` ON `records` (`measureTime`, `id`)")
        db.execSQL("CREATE INDEX IF NOT EXISTS `index_records_period_measureTime_id` ON `records` (`period`, `measureTime`, `id`)")
    }
}
```

```kotlin
// GlucoNoteApp.kt —— 明确注册迁移，绝不用 destructive
Room.databaseBuilder(this, AppDatabase::class.java, AppDatabase.DATABASE_NAME)
    .addMigrations(MIGRATION_1_2)
    .build()
```

**关键细节**：Room 启动时会校验实际表结构与实体声明是否一致。索引名对不上会直接抛 `IllegalStateException`。所以 `@Index(name = ...)` 与 `execSQL` 里的名字必须逐字一致，建议按 Room 默认命名规则 `index_<表>_<列1>_<列2>` 书写。

**为什么第二个索引是 `(period, measureTime, id)`**：记录页最常见的组合是「选中某标签 + 时间倒序分页」。这个复合索引既能满足 `WHERE period = ? ORDER BY measureTime DESC, id DESC`，也能被 `(period)` 前缀复用。

#### 1.3 schema 快照

打开 `exportSchema = true` 后，KSP 会把 schema JSON 输出到 `app/schemas/`，**必须提交进 git**。之后任何字段/索引变更都能 diff 出差异，也是写 Migration 的唯一依据。

#### 1.4 回滚风险（务必知晓）

DB 升到 v2 后，**装回旧版 APK（v1.2.4 及以前）会启动失败**——Room 检测到磁盘版本高于代码版本会抛异常。可选处理：
- 方案 A（推荐）：接受不可降级，在 Release Notes 注明。
- 方案 B：加 `fallbackToDestructiveMigrationOnDowngrade()`，降级时清库（会丢数据，不推荐用于健康记录）。

**发版前要求用户先「导出 CSV」备份**，这是唯一的兜底。

### 阶段二：把全量加载改成按需查询（P1）

原则：**能用 SQL 算的不要搬到内存算**；必须逐点处理的（趋势图）限定窗口与列。

#### 2.1 首页：3 条小查询

```kotlin
data class HomeSummary(
    val todayCount: Int,
    val weekCount: Int,
    val weekAvg: Float?,
    val lastValue: Float?,
    val lastPeriod: String?
)

@Query("""
    SELECT
      (SELECT COUNT(*) FROM records WHERE measureTime >= :startToday) AS todayCount,
      (SELECT COUNT(*) FROM records WHERE measureTime >= :weekAgo)    AS weekCount,
      (SELECT AVG(value) FROM records WHERE measureTime >= :weekAgo)  AS weekAvg,
      (SELECT value  FROM records ORDER BY measureTime DESC LIMIT 1)  AS lastValue,
      (SELECT period FROM records ORDER BY measureTime DESC LIMIT 1)  AS lastPeriod
""")
fun observeHomeSummary(startToday: Long, weekAgo: Long): Flow<HomeSummary>

@Query("SELECT * FROM records ORDER BY measureTime DESC LIMIT 5")
fun observeRecent5(): Flow<List<GlucoseRecord>>
```

`HomeViewModel` 用 `combine(summary, recent5, settings)` 组装，**不再触碰全表**。

#### 2.2 统计：达标率与区间聚合交给 SQL

```kotlin
data class PeriodRateRow(val period: String, val total: Int, val inRange: Int)

@Query("""
    SELECT period,
           COUNT(*) AS total,
           SUM(CASE
                 WHEN period = 'fasting' AND value BETWEEN :fMin AND :fMax THEN 1
                 WHEN period <> 'fasting' AND value BETWEEN :pMin AND :pMax THEN 1
                 ELSE 0
               END) AS inRange
    FROM records
    WHERE measureTime BETWEEN :from AND :to
    GROUP BY period
""")
suspend fun rateByPeriod(from: Long, to: Long, fMin: Float, fMax: Float, pMin: Float, pMax: Float): List<PeriodRateRow>

@Query("""
    SELECT AVG(value) AS avg, MAX(value) AS max, MIN(value) AS min, COUNT(*) AS count,
           AVG(value * value) AS avgSq
    FROM records
    WHERE measureTime BETWEEN :from AND :to
""")
suspend fun rangeStats(from: Long, to: Long): RangeStatsRow?   // std = sqrt(avgSq - avg*avg)
```

> 注意：达标判定与 `StatsUtils.levelOf()` 的语义必须完全一致（空腹用 fasting 区间，其余用 post 区间）。改动后要保证**内存算法仍然保留**并做对拍测试（见 §6）。

#### 2.3 趋势与桶：限定窗口 + 轻量列

`computeTrend` 在「近 1 年」下会返回约 1800 个点。两点优化：
1. 只 `SELECT measureTime, value, period`（新增轻量 DTO），不构造完整实体；
2. 点数超过阈值（建议 400）时按天聚合后再给图表，宁可少画点。

桶统计（`computeBucketStats`）建议**保留在 Kotlin 做**：SQL 分组要用 `strftime(...,'unixepoch','localtime')`，本地时区与 DST 容易出错，收益不抵风险。但必须**限定窗口**（DAY 粒度只看最近 60 天，MONTH 看最近 24 个月），否则 YEAR 粒度仍会扫全表。

#### 2.4 刷新机制修正（P1-1，正确性问题）

现状：`observeCount()` 只在行数变化时触发重载 → 编辑不刷新、且 `softReload` 会重放分页。

建议改为「变更版本号」：

```kotlin
@Query("SELECT COUNT(*) * 1000000 + COALESCE(MAX(createdAt), 0) FROM records")
fun observeChangeToken(): Flow<Long>
```

- 行数变化（插入/删除）→ token 变；
- 编辑会刷新 `createdAt`（`upsert` 已写入新 `createdAt`）→ token 也变。

配套把 `softReload` 的「重放分页」改成「回到第一页」或「按时间窗重新查询已加载区间」，避免已加载 500 条时一次写入触发 20 次查询。

> 若不想动 DAO，最小修法：`AddRecordViewModel.commit()` 成功后回调记录页 `refresh()`。但这只是打补丁，跨 Tab 场景仍会漏。

#### 2.5 SQL 与内存算法的关系

`StatsUtils.kt` 里的纯函数**不要删**：它们可单测、是 SQL 结果的参照实现。做法：
- SQL 只负责「筛 + 聚合」；
- 若个别聚合（如桶）暂时留在 Kotlin，也改成「接收已裁剪窗口的小列表」。

#### 2.6 分页查询拆分（可选清理项，P2-2）

`pageAfter` 用 `(:period IS NULL OR period = :period)` 一个方法覆盖「全部/单标签」两种情况，代价是优化器无法针对 `period` 做索引定位（实测走 `measureTime` 索引 + 回表过滤）。拆成两个方法即可让复合索引用上：

```kotlin
@Query("""SELECT * FROM records
  WHERE measureTime < :cursorTime OR (measureTime = :cursorTime AND id < :cursorId)
  ORDER BY measureTime DESC, id DESC LIMIT :limit""")
suspend fun pageAll(cursorTime: Long, cursorId: String, limit: Int): List<GlucoseRecord>

@Query("""SELECT * FROM records
  WHERE period = :period
    AND (measureTime < :cursorTime OR (measureTime = :cursorTime AND id < :cursorId))
  ORDER BY measureTime DESC, id DESC LIMIT :limit""")
suspend fun pageByPeriod(period: String, cursorTime: Long, cursorId: String, limit: Int): List<GlucoseRecord>
```

实测 18k 行：带标签查询 0.044 ms → 0.025 ms（1.8×），执行计划由 `SEARCH ... USING INDEX index_records_measureTime_id (measureTime<?)` 变为 `SEARCH ... USING INDEX index_records_period_measureTime_id (period=? AND measureTime<?)`。

**优先级低**：绝对耗时差 < 0.02 ms，用户不可感知。若不想动分页逻辑，可以不做。

### 阶段三：长期项（可选，按需）

| 项 | 做法 | 收益 | 成本 | 建议 |
|----|------|------|------|------|
| value 存整数 | `valueX10: Int`，读出时 `/10f`；CSV 兼容两种写法 | 每行省 4 B、比较更快 | 迁移 + 全链路改动 | 暂缓（收益小） |
| 主键瘦身 | 自增 `Long rowid` 主键 + `uid TEXT` 唯一列 | 索引更小、B 树更快 | 迁移复杂、CSV id 语义要保 | 暂缓 |
| PRAGMA 调优 | `synchronous = NORMAL`（WAL 默认已开） | 批量写更快、掉电最多丢最后一笔 | 低 | 可与阶段一一起做 |
| 数据库加密 | SQLCipher（新增依赖） | 静态数据保护 | 与「离线构建/APK 体积」冲突，需评估 | 按合规要求定 |
| 自动备份 | 每周自动导出 CSV 到 SAF 或私有目录滚动保留 3 份 | 灾备 | 中 | 建议排期 |
| 导出流式化 | 用 Cursor 分批拼串，避免全量驻留 | 峰值内存下降 | 中 | 3.6 万条以上才有必要 |

## 6. 验证方案

### 6.1 单测（无需新增依赖）

1. **SQL 语义对拍**：把 `testdata/gluconote_testdata_3y.csv` 解析成内存列表，用现有 `StatsUtils` 算出的达标率/均值/极值，与 SQL 版本对齐（SQL 部分在无 Android 环境跑不了，改为对拍「同一份数据的两种 Kotlin 实现」，并把 SQL 的 CASE 逻辑抽成纯函数共享）。
2. **`levelOf` 边界**：`value == min`、`value == max`、空腹 vs 餐后阈值不同 —— 确保 `BETWEEN`（闭区间）与 Kotlin 的 `<`/`>` 一致。
3. **`observeChangeToken`**：插入 +1、删除 -1、编辑（createdAt 变化）token 必须变。

### 6.5 基准实测记录（2026-10-27）

用于定级的数据，**已实测**，不是估算。环境：Windows 11 + Python 3.13 `sqlite3`（文件型库，含 fsync），数据集为 `testdata/gluconote_testdata_3y.csv`（5040 条）。

**① 导入：逐条事务 vs 批量单事务（1000 条样本，外推 5040）**

| 方式 | 1000 条耗时 | 每条 | 外推 5040 条 | 倍数 |
|------|-----------|------|-------------|------|
| 逐条 `insert` + `commit` | 43,770 ms | 43.77 ms | ≈ 220 s | 1× |
| 批量（单事务，400/块） | 44.6 ms | 0.045 ms | ≈ 0.22 s | **981×** |

> 说明：这台机器的 fsync 偏慢（43 ms/次），Android 的 ext4/f2fs 通常 0.5–5 ms，故真机预期为 **10–100×**，而非 981×。但「逐条 vs 批量」的数量级差异在真机上同样成立——**这是本方案最重要的一项**。

**② 分页查询（18,250 行，10 年 × 5 次/天）**

| 查询 | 耗时 | 执行计划 |
|------|------|---------|
| 不筛选标签（现状） | 0.034 ms | `SEARCH USING index_records_measureTime_id (measureTime<?)` |
| 不筛选标签（拆分后） | 0.025 ms | 同上 |
| 筛选标签（现状，`? IS NULL OR`） | 0.044 ms | `SEARCH USING index_records_measureTime_id` + 回表过滤 |
| 筛选标签（拆分后） | 0.025 ms | `SEARCH USING index_records_period_measureTime_id (period=? AND measureTime<?)` |

**结论修正**：在 1.8 万行量级，分页本身只有几十微秒，**索引与查询拆分都不是当前瓶颈**。索引的真正价值是防止数据量继续增长后的退化（临时 B 树排序、全表扫），以及给 `getBetween` 范围查询兜底——所以它仍然要做，但不要把收益说大。

**③ 变更令牌有效性**（5040 行数据）

| 操作 | token 是否变化 |
|------|--------------|
| `UPDATE ... SET createdAt = now`（模拟编辑） | 变 |
| `DELETE` 一行 | 变 |

结论：`COUNT(*) * 1000000 + MAX(createdAt)` 能同时捕获「增删」与「编辑」，可以作为刷新信号替代现有 `observeCount()`。

## 8. 预期收益

| 指标 | 现状 | 目标 | 依据 |
|------|------|------|------|
| 导入 5040 条 | 5040 次事务 | 1 次事务（内部 13 个 INSERT） | 实测 981×（本机），真机预期 10–100× |
| 记录页首屏查询 | 索引可用但未针对 period 优化 | 索引定位 25 条 | 实测 0.044 → 0.025 ms（当前非瓶颈） |
| 写入后的重算 | 全表加载 + 6~8 次遍历 | 1 次窗口查询 + 2 次聚合 | 结构性改动，随数据量放大收益 |
| 编辑可见性 | 需重进页面 | 立即刷新 | 实测 token 可捕获编辑 |
| 可演进性 | 无 schema 快照 | 版本化 schema + Migration | 消除「升级即崩」风险 |

### 8.1 一句话优先级

**先做导入事务（收益最大、风险最低、不碰 schema），再做「编辑不刷新」的正确性修复；索引与迁移基建一并做；统计页 SQL 化放在第三批，因为它改动面最大且当前性能尚可。**
