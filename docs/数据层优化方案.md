# GlucoNote 数据层性能优化方案（开发期版）

> **v2 · 2026-10-27**
> **前提已变更**：项目处于开发阶段、无正式数据 → **不受数据兼容约束**，可破坏性重建库、可自由调整表结构。
> **首要目标**：大数据量（设计上限 **20 万行**）下的**查询与计算性能**，而非存储体积或迁移兼容。

---

## 1. 目标（以 20 万行为基准）

| 场景 | 现状（实测，见 §2） | 目标 |
|------|------------------|------|
| 记录页首屏（第 1 页 25 条） | **69.7 ms**（无索引，掉帧） | < 1 ms |
| 统计页一次刷新（5 组指标） | **≈ 286 ms**（全量拉取 + 内存聚合，且每次写入都重算） | < 20 ms |
| 导入 20 万条 | 逐条事务（外推约 2 小时级） | < 3 s |
| 近 1 年趋势 | 1825 个点直绘 | ≤ 400 点（按天聚合） |
| 任意写入 | 全表重新加载 + 全量重算 | 只跑窗口查询 |

---

## 2. 实测基线（先看数据）

**环境**：Windows 11 + Python 3.13 `sqlite3`，内存库，20 万行合成数据（10 年 × 55 次/天）。
**说明**：这是关系型数据库行为的代理基准。Android 真机 I/O 更慢、Kotlin 对象分配与 Python 不同，**绝对毫秒会变，但相对差距与执行计划一致**。

### 2.1 索引：读写两端的关键杠杆

| 操作（20 万行） | 无索引 | 有索引 | 倍数 |
|----------------|--------|--------|------|
| 记录页第 1 页（排序 + LIMIT 25） | **69.70 ms** | **0.024 ms** | **2900×** |
| 近 30 天区间聚合（AVG/MAX/MIN/COUNT） | 8.08 ms | **0.02 ms**（覆盖索引） | **400×** |
| 按标签筛选分页 | 0.039 ms（走 measureTime 索引 + 回表） | 0.025 ms（走复合索引） | 1.6× |

> 无索引时 `ORDER BY measureTime DESC LIMIT 25` 必须**扫全表 + 临时 B 树排序**，20 万行 70 ms —— 已超出 16 ms 帧预算，列表会明显卡顿。

### 2.2 计算位置：SQL 聚合 vs 拉全表到内存

| 方式 | 20 万行耗时 | 说明 |
|------|-----------|------|
| 全量 `SELECT *` + 内存聚合（≈ 现在 `observeAll()` + `StatsUtils`） | **285.9 ms** | 还要再乘上「filter 两次 + 5 个聚合函数各遍历一次」 |
| SQL 聚合（区间统计 + 达标率 GROUP BY） | **16.43 ms** | 且只返回几行结果 |

**17× 差距**，而且现在实现比这个代理更糟：`StatsViewModel` 拿到全量列表后，`computeTrend` / `computeRateByPeriod` / `computeBucketStats` / `computeRangeStats × 2` 各自 filter+map 一遍。

### 2.3 趋势点数

| 方式 | 耗时 | 点数 |
|------|------|------|
| 近 1 年原始点 | 9.30 ms | 1825 |
| 近 1 年按天聚合 | 8.58 ms | 365 |

SQL 耗时接近，但**传输 5 倍数据 + Canvas 绘制 5 倍图元**，触摸命中测试成本线性增长。按天聚合稳赚。

### 2.4 导入

| 方式 | 1000 条 / 20 万条 | 每条 |
|------|-----------------|------|
| 逐条 `insert` + 每次提交 | 43,770 ms（1000 条样本） | 43.77 ms |
| 单事务批量（无索引） | 687 ms（20 万条） | 0.0034 ms |
| 单事务批量（3 个索引） | 1,305 ms（20 万条） | 0.0065 ms |

- **逐条 vs 批量 ≈ 981×**（本机 fsync 偏慢；Android 预期 10–100×，量级关系不变）
- 索引让导入成本约 **+90%**（687 → 1305 ms），但换来读取 2900×，**这笔交易明显划算**
- 批量块大小：400 条 786 ms、1000 条 811 ms、2000 条 1803 ms、5000 条 1510 ms → **现有 400 条/块无需调整**

### 2.5 深分页

| 方式 | 第 201 页 |
|------|----------|
| `OFFSET 5000` | 0.14 ms |
| keyset 游标（现状已用） | 0.022 ms |

现有 keyset 分页设计**正确**，不需要改。

## 4. 问题与优先级（按 20 万行重新定级）

| 优先级 | 问题 | 实测影响 | 目标 |
|--------|------|---------|------|
| **P0-1** | 无任何索引 | 分页 69.7 ms（2900×）、聚合 8.08 ms（400×） | 加 3 个索引 |
| **P0-2** | 首页/统计 `observeAll()` 全量 + 内存聚合 | 286 ms/次，且每次写入都触发 | 全部改 SQL 聚合 |
| **P0-3** | 导入逐条事务 | 981× | 单事务批量 |
| **P1-1** | 统计对同一列表重复遍历 6~8 次 | 与 P0-2 叠加放大 | 合并为 1 次查询 |
| **P1-2** | 编辑后列表不刷新（仅监听 count） | 正确性问题 | 改变更令牌 |
| **P1-3** | `softReload` 重放分页 | 已加载 500 条时一次写入重放 20 次查询 | 回到第一页或按窗口重查 |
| **P1-4** | 趋势直绘 1825 点 | 绘制/命中测试成本线性 | 超 400 点按天下采样 |
| **P2-1** | `(:period IS NULL OR period = :period)` 使复合索引失效 | 0.039 → 0.025 ms（1.6×，绝对值小） | 拆两条查询 |
| **P2-2** | `value` REAL / `id` TEXT | 写放大，索引条目更大 | 开发期可改 `valueX10 INT` + 自增主键 |
| **P2-3** | DB 明文 | 合规风险 | 上架前评估 |

## 5. 方案

### 阶段 A：索引 + 写入路径（P0，收益最大、风险最低）

#### A.1 三个索引（开发期直接破坏性重建，不写 Migration）

```kotlin
@Entity(
    tableName = "records",
    indices = [
        // 记录页：全部标签，按时间倒序 + id 破平
        Index(value = ["measureTime", "id"], name = "idx_measureTime_id"),
        // 记录页：单标签筛选
        Index(value = ["period", "measureTime", "id"], name = "idx_period_measureTime_id"),
        // 统计：区间聚合 / 趋势 / 达标率 的覆盖索引
        Index(value = ["measureTime", "value", "period"], name = "idx_cover_time_value_period")
    ]
)
```

**覆盖索引是 400× 的来源**：聚合只需 `measureTime / value / period` 三列，索引本身包含这三列时 SQLite 走 `SEARCH ... USING COVERING INDEX`，**完全不需要回表**。

```kotlin
// AppDatabase.kt
@Database(entities = [GlucoseRecord::class], version = 2, exportSchema = false)
```

```kotlin
// GlucoNoteApp.kt —— 开发期专用：版本变化直接重建（无数据可丢）
Room.databaseBuilder(this, AppDatabase::class.java, AppDatabase.DATABASE_NAME)
    .fallbackToDestructiveMigration()   // ⚠️ 上架前必须替换为 addMigrations(...)
    .build()
```

#### A.2 导入走单事务批量

```kotlin
// RecordRepository
suspend fun importAll(records: List<GlucoseRecord>) = withContext(Dispatchers.IO) {
    db.withTransaction {
        records.chunked(400).forEach { db.recordDao().insertIgnore(it) }
    }
}
```

```kotlin
// RecordDao —— 导入用 IGNORE：不做 DELETE+INSERT，比 REPLACE 少一半索引维护
@Insert(onConflict = OnConflictStrategy.IGNORE)
suspend fun insertIgnore(records: List<GlucoseRecord>)
```

> `OnConflictStrategy.REPLACE` 在 SQLite 里是 **DELETE + INSERT**，会让索引条目反复删除重建，这是「逐条导入慢」的第二层原因。导入用 `IGNORE` 更合适：重复 id 跳过，不覆盖用户已编辑的数据。

```kotlin
// ProfileViewModel
suspend fun importText(text: String): Int {
    val list = parseCsv(text)
    repo.importAll(list)
    return list.size
}
```

#### A.3 大批量导入后 `ANALYZE`

```kotlin
// 导入完成后刷新优化器统计信息，避免选错索引
suspend fun analyze() = withContext(Dispatchers.IO) {
    db.openHelper.writableDatabase.execSQL("ANALYZE")
}
```

#### A.4 写放大权衡（记录在案）

索引让 20 万条导入从 687 ms 变 1305 ms（+90%），但：
- 导入是一次性动作，1.3 s 可接受；
- 读是每次打开页面都发生，2900× 的收益必须拿。

因此**不要为了导入速度砍索引**。只有单次导入超过 50 万条才值得考虑「导入前 DROP INDEX + 导入后重建」（本项目不必要）。

### 阶段 B：查询重构（P0，去掉所有全量拉取）

#### B.1 首页：一次聚合 + 一次 TOP-N

```kotlin
data class HomeSummary(
    val todayCount: Int, val weekCount: Int,
    val weekAvg: Float?, val lastValue: Float?, val lastPeriod: String?
)

@Query("""
    SELECT
      (SELECT COUNT(*) FROM records WHERE measureTime >= :startToday) AS todayCount,
      (SELECT COUNT(*) FROM records WHERE measureTime >= :weekAgo)    AS weekCount,
      (SELECT AVG(value) FROM records WHERE measureTime >= :weekAgo)  AS weekAvg,
      (SELECT value  FROM records ORDER BY measureTime DESC LIMIT 1)  AS lastValue,
      (SELECT period FROM records ORDER BY measureTime DESC LIMIT 1)  AS lastPeriod
""")
fun observeHomeSummary(startToday: Long, weekAgo: Long): Flow<HomeSummary>

@Query("SELECT * FROM records ORDER BY measureTime DESC LIMIT 5")
fun observeRecent5(): Flow<List<GlucoseRecord>>
```

`HomeViewModel` = `combine(summary, recent5, settings)`，**不再 `observeAll()`**；时间窗参数由 `MutableStateFlow` 提供，跨天刷新。

#### B.2 统计：达标率与区间聚合交给 SQL

```kotlin
data class PeriodRateRow(val period: String, val total: Int, val inRange: Int)

@Query("""
    SELECT period,
           COUNT(*) AS total,
           SUM(CASE
                 WHEN period =  'fasting' AND value BETWEEN :fMin AND :fMax THEN 1
                 WHEN period <> 'fasting' AND value BETWEEN :pMin AND :pMax THEN 1
                 ELSE 0
               END) AS inRange
    FROM records
    WHERE measureTime BETWEEN :from AND :to
    GROUP BY period
""")
suspend fun rateByPeriod(from: Long, to: Long, fMin: Float, fMax: Float, pMin: Float, pMax: Float): List<PeriodRateRow>

data class RangeStatsRow(val avg: Float?, val max: Float?, val min: Float?, val count: Int, val avgSq: Float?)

@Query("""
    SELECT AVG(value) AS avg, MAX(value) AS max, MIN(value) AS min,
           COUNT(*) AS count, AVG(value * value) AS avgSq
    FROM records
    WHERE measureTime BETWEEN :from AND :to
""")
suspend fun rangeStats(from: Long, to: Long): RangeStatsRow?
// std = sqrt(avgSq - avg*avg)，SQLite 无 STDDEV，用二阶矩换算
```

> 语义必须与 `StatsUtils.levelOf()` 一致：**空腹用 fasting 区间，其余（含睡前）用 post 区间**；`BETWEEN` 是闭区间，与 Kotlin 的 `<` / `>` 判定等价（§7.1 用单测锁住）。

#### B.3 趋势：下采样 + 轻量列

```kotlin
// 分桶用 UTC 天序，避开 SQLite localtime 的时区/DST 坑
@Query("""
    SELECT (measureTime / 86400000) AS day,
           AVG(value) AS avg, MAX(value) AS max, MIN(value) AS min, COUNT(*) AS count
    FROM records
    WHERE measureTime BETWEEN :from AND :to
    GROUP BY day
    ORDER BY day
""")
suspend fun dailyTrend(from: Long, to: Long): List<DailyPoint>
```

策略：
- 期望点数 = `rangeType` 天 × 每天次数；
- 期望点数 > **400** → 走 `dailyTrend`；否则走原始点（只 `SELECT measureTime, value, period`，不构造完整实体）；
- 图表统一按「点 + 可选 min/max 带状」渲染。

#### B.4 桶统计：留在 Kotlin，但只给小窗口

`computeBucketStats` 分组留在 Kotlin（保留可测性），但必须**限定输入规模**：

| 粒度 | 输入窗口 |
|------|---------|
| DAY | 最近 60 天 |
| MONTH | 最近 24 个月 |
| YEAR | 最近 10 年（≈1.8 万行，仍可接受） |

不做 SQL 分组的理由：需 `strftime(..., 'unixepoch', 'localtime')` 对齐本地日历日，时区/DST 边界易错，收益不抵风险。

#### B.5 刷新机制：变更令牌替代 count

```kotlin
@Query("SELECT COUNT(*) * 1000000 + COALESCE(MAX(createdAt), 0) FROM records")
fun observeChangeToken(): Flow<Long>
```

- 增删 → count 变，token 变；
- **编辑** → `upsert` 刷新 `createdAt` → token 变（实测有效）。

`StatsViewModel` / `HomeViewModel` 用它作为「重查」信号；`RecordsViewModel` 用它替代 `observeCount`，同时把 `softReload` 的重放分页改为**回到第一页**（或按 `measureTime` 窗口重查已加载区间）。

#### B.6 统计页状态流：`flatMapLatest` 防抖

```kotlin
data class StatsQuery(val period: String?, val range: RangeType, val gran: Granularity, val settings: Settings, val token: Long)

val ui: StateFlow<StatsUiState> = combine(
    filterPeriod, rangeType, granularity, settingsRepo.settingsFlow, repo.observeChangeToken()
) { p, r, g, s, t -> StatsQuery(p, r, g, s, t) }
    .distinctUntilChanged()
    .flatMapLatest { q -> flow { emit(loadStats(q)) } }   // 切参数时取消上一次查询
    .flowOn(Dispatchers.IO)
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), StatsUiState())
```

`flatMapLatest` 解决「快速切换 7 天/30 天/1 年时旧查询排队返回、画面闪回」的问题。

### 阶段 C：可选进阶（20 万行以上再考虑）

| 项 | 适用条件 | 做法 |
|----|---------|------|
| 聚合结果短时缓存 | 频繁切页但数据不变 | `MutableStateFlow` 存 `(queryHash → result)`，token 变化即失效 |
| 预聚合表 | 百万行级 | 按 `(天, period)` 维护 `daily_summary`，统计只查汇总表 |
| 导入期临时删索引 | 单次导入 > 50 万条 | `DROP INDEX` → 导入 → `CREATE INDEX` + `ANALYZE` |
| `valueX10 INT` | 追求极限 | 省 4 B/行、比较更快，CSV/UI 需同步改 |

## 7. 验证与压测

### 7.1 单测（不加依赖）

1. **语义对拍**：SQL 的 `CASE` 达标判定抽成纯函数，与 `StatsUtils.levelOf()` 用同一份数据断言一致；边界 `value == min` / `value == max`。
2. **std 换算**：`sqrt(avgSq - avg²)` 与 `statsOf` 方差公式结果在 1e-4 内一致，需 `coerceAtLeast(0f)` 防浮点负值。
3. **下采样阈值**：期望点数 > 400 走日聚合，否则走原始点。

### 7.2 压测数据

```bash
# 18k（10 年 × 5 次/天）
python3 testdata/gen_large_csv.py --years 10 --per-day 5 --out testdata/large_18k.csv

# 200k（10 年 × 55 次/天，约 16 MB）
python3 testdata/gen_large_csv.py --years 10 --per-day 55 --out testdata/large_200k.csv
```

导入后逐页记录（`measureTimeMillis` 日志或 `dumpsys gfxinfo`）：
记录页首屏 / 滚到第 200 页 / 统计页切 7 天·30 天·1 年 / 首页首屏 / 导入总耗时。

**验收线**：记录页首屏 < 16 ms、统计页一次刷新 < 50 ms、导入 20 万条 < 3 s。

## 10. ⚠️ 上架前必须回切的清单

开发期用破坏性重建换速度，**正式发布前必须逐项改回**：

- [ ] `fallbackToDestructiveMigration()` → `addMigrations(MIGRATION_X_Y)`（用户数据不可丢）
- [ ] `exportSchema = false` → `true`，`app/schemas/` 提交进版本库
- [ ] 每次表结构变更配 `Migration`，并写「升级安装」手工用例
- [ ] 迁移前引导用户导出 CSV 备份（Release Notes 提示）
- [ ] 若保留 `valueX10 INT` 方案，`Csv.kt` 需兼容两种精度
