# 版本管理与应用内更新

本文说明 GlucoNote 的**版本号规则、发版流程、分发渠道、应用内更新机制**。整体设计与 WindTone（听风）保持一致，便于两个项目共用同一套心智模型与运维手法。

---

## 1. 全景图

```

                     │  app/build.gradle.kts（版本号唯一来源）      │

                     └───────────────┬─────────────────────────────┘
```

## 2. 版本号规则（单一来源）

版本号定义在 `app/build.gradle.kts` 的**文件顶部**（不在 `defaultConfig` 里、也不进 Version Catalog）：

```kotlin
// 版本号单一来源：改版本只改这两行即可（scripts/release.sh 与 CI 都按此格式解析）。
// ⚠️ 故意不放进 Version Catalog：release.sh 用 grep 按固定文本格式解析。
val appVersionName = "1.0.0"
val appVersionCode = 1
```

`defaultConfig` 里只是引用：

```kotlin
versionCode = appVersionCode
versionName = appVersionName
```

### 为什么必须放这里

| 消费者 | 依赖方式 | 说明 |
|---|---|---|
| `scripts/release.sh` | `grep -E '^val appVersionName = '` | 用固定文本格式解析、`sed` 回写 |
| `.github/workflows/build-release.yml` | 同上（一致性闸门、`CODE` 取值） | tag 与 `appVersionName` 不一致直接报错退出 |
| `BuildConfig.VERSION_NAME / VERSION_CODE` | 编译期注入 | 应用内更新用它判断「有没有新版本」 |

**一旦移进 `gradle/libs.versions.toml`，上面三条链路全部失效**（grep 拿不到、CI 闸门失效、`versionName` 引用需要改写法）。第三方依赖版本进 catalog，产品版本留在这里 —— 这是刻意的分野。

### 两个号的含义

| 字段 | 规则 | 谁在用它 |
|---|---|---|
| `appVersionName` | 语义化版本 `X.Y.Z`，与 git tag `vX.Y.Z` **必须一致** | 人看的；`latest.json` 的 `version`；更新判断的主依据 |
| `appVersionCode` | 单调递增整数，每次发版 +1 | 系统安装器用它判断"升级还是降级"；**绝不能回退** |

> ⚠️ `appVersionCode` 一旦发布过就不能改小，否则系统会拒绝覆盖安装。

## 3. 发版流程

### 3.1 一条命令（推荐）

```bash
bash scripts/release.sh patch    # 1.0.0 -> 1.0.1
bash scripts/release.sh minor    # 1.0.0 -> 1.1.0
bash scripts/release.sh major    # 1.0.0 -> 2.0.0
bash scripts/release.sh set 1.2.3
```

### 3.2 `release.sh` 做了什么

按顺序执行，**任何一步失败立即中止**：

1. 从 `app/build.gradle.kts` 解析当前 `appVersionName` / `appVersionCode`
2. 按 mode 计算新版本与新 code（`code + 1`）
3. **检查工作区必须干净**（有未提交改动直接退出，避免把无关改动裹进 release 提交）
4. **检查 tag 尚未存在**（重复 tag 会污染历史）
5. 检查 `JAVA_HOME`：本机默认 JDK 不满足 Gradle 要求时自动指向 `~/.jdks/openjdk-21.0.2`
6. **先跑单测**：`./gradlew testDebugUnitTest --offline` —— **测试不过不许发版**
7. `sed` 回写版本号两行
8. `git commit -m "release: v1.0.1"`
9. `git tag v1.0.1`
10. `git push origin main "v1.0.1"` —— **这一步触发 CI**
11. **推后实查**：调 GitHub REST 确认 tag 真的出现在远端（最多重试 3 次）

> 第 6 步是刻意的顺序：**先验证、后改版本号**。反过来的话，测试失败会在历史里留下一个"版本号改了但没发出去"的脏提交。

### 3.3 手动发版（不推荐，但要知道）

```bash
# 1. 手动改 app/build.gradle.kts 两行（versionName 与 versionCode 都要改）
# 2. 本地全绿
./gradlew assembleDebug testDebugUnitTest
# 3. 提交并打 tag（tag 必须与 versionName 一致，否则 CI 闸门会拦下）
git add app/build.gradle.kts && git commit -m "release: v1.0.1"
git tag v1.0.1 && git push origin main v1.0.1
```

## 4. CI 流水线

文件：`.github/workflows/build-release.yml`

### 4.1 两个 job 的分工

| Job | 触发条件 | 干什么 | 产物 |
|---|---|---|---|
| `verify` | push 到 `main` | `assembleDebug` + `testDebugUnitTest` | 无（只验证） |
| `release` | push `v*` tag 或手动触发 | 构建签名包 → 发布到公共仓库 | APK + `latest.json` |

### 4.2 Android SDK 的安装方式（踩过的坑）

**不能**再用 `android-actions/setup-android@v3` —— 它会尝试安装早已废弃的 `tools` 包，报 `Failed to find package 'tools'`。改为直接调运行器预装 SDK 里的 `sdkmanager`：

```yaml
- name: Set up Android SDK
  env:
    ANDROID_HOME: /usr/local/lib/android/sdk
  run: |
    SDKMANAGER=$(ls "$ANDROID_HOME"/cmdline-tools/*/bin/sdkmanager 2>/dev/null | head -1)
    yes | "$SDKMANAGER" --licenses > /dev/null || true
    "$SDKMANAGER" "platforms;android-34" "build-tools;34.0.0"
```

### 4.3 发版闸门：tag ↔ versionName 一致性

```yaml
- name: Check tag & versionName consistency
  run: |
    VERSION="${GITHUB_REF_NAME#v}"
    FILE_VERSION=$(grep -E '^val appVersionName = ' app/build.gradle.kts | head -1 | grep -o '[0-9][0-9.]*')
    if [[ "$VERSION" != "$FILE_VERSION" ]]; then
      echo "::error::tag 版本（$VERSION）与 appVersionName（$FILE_VERSION）不一致"
      exit 1
    fi
```

**为什么必须有这一道**：应用内更新的判断依据是「`latest.json` 的 `version`」对比「`BuildConfig.VERSION_NAME`」。如果 tag 写 `v1.0.5` 而 `versionName` 还是 `1.0.4`，发布出去的包会**永远认为自己是 1.0.4**，用户装上后仍被提示"有新版本"，陷入无限更新循环。闸门把这个可能性在 CI 阶段就掐死。

### 4.4 release job 的完整步骤

1. Checkout → JDK 17 → Android SDK
2. **tag 一致性闸门**
3. 从 Secret `KEYSTORE_BASE64` 解码 keystore
4. `./gradlew clean assembleRelease`（签名信息来自 `KEYSTORE_PATH / KEYSTORE_PASSWORD / KEY_ALIAS / KEY_PASSWORD`）
5. **统一产物命名**：`GlucoNote-v<版本>.apk`
6. 写 `/tmp/notes.md` 作为更新说明
7. 调 `scripts/publish-release-repo.sh` 发布到公共仓库

## 5. 分发仓库结构

公共仓库：`https://github.com/LuckyLearning/Release`（**无需任何鉴权即可读取**）

```
Release/
├─ README.md                       # 由 gen-release-manifest.py 自动生成，勿手改
├─ GlucoNote/
│  ├─ latest.json                  # ← 应用内更新读这个
│  ├─ v1.0.1/
│  │  ├─ GlucoNote-v1.0.1.apk
│  │  ├─ notes.md
│  │  └─ checksums.txt             # 各包 SHA-256
│  ├─ v1.0.0/
│  └─ …（最多 5 个版本目录）
└─ WindTone/                       # 同仓库的另一个软件
```

### 5.1 为什么用静态文件而不是 GitHub Release

| 维度 | GitHub Release（旧方案） | 静态文件 + latest.json（现方案） |
|---|---|---|
| 匿名可读 | 私有仓库的 Release 匿名读不到 | raw 直链，**零鉴权** |
| API 配额 | REST API 每小时 60 次 | `raw.githubusercontent.com` 是 CDN，**不占配额** |
| 校验能力 | 只能拿资产名/大小 | 清单里带**每个包的 SHA-256** |
| 客户端复杂度 | 要解析 Release 列表 | 一次 GET 一个 JSON |

### 5.2 保留策略：只留最近 5 个版本

`publish-release-repo.sh` 每次发布时：

1. 按语义版本排序，删掉第 6 个及更旧的目录
2. 用 `--orphan` 建一个孤立分支提交，`push -f` 覆盖 `main`

> **这是"快照式"发布**：仓库体积恒定在约 5 个版本，历史二进制不会无限堆积。
> 代价是公共仓库的 `main` **不能开分支保护**（否则 force push 被拒）。

### 5.3 `latest.json` 结构

```json
{
  "schema": 1,
  "app": "GlucoNote",
  "displayName": "血糖随手记 GlucoNote",
  "version": "1.0.1",
  "versionCode": 2,
  "tag": "v1.0.1",
  "publishedAt": "2026-10-26T10:00:00Z",
  "minSdk": 26,
  "notes": "## 本次更新\n- …",
  "assets": [
    {
      "file": "GlucoNote-v1.0.1.apk",
      "size": 5678901,
      "sha256": "abc123…"
    }
  ]
}
```

**前向兼容约定**：`schema` 只用于"忽略未知字段"。这是**分发渠道**，客户端散落在各个旧版本上，**新增字段必须可选，旧客户端不能被新清单弄崩**。

## 6. 应用内更新

### 6.1 代码位置

| 文件 | 职责 |
|---|---|
| `app/src/main/java/com/gluconote/update/UpdateChecker.kt` | 检查 → 下载 → 校验 → 拉起安装器 |
| `app/src/main/java/com/gluconote/ui/profile/UpdateCard.kt` | 「我的 → 版本更新」卡片 UI |
| `app/src/main/res/xml/file_paths.xml` | FileProvider 路径声明 |

### 6.2 数据流

```
用户点「检查更新」
   │
   ├─ 第一轮（tier 0，不缓存的线路）并发竞速
   │    raw.githubusercontent.com ／ ghfast.top ／ gh-proxy.com
   │    ghproxy.net ／ gh.llkk.cc          —— 谁先返回合法清单就用谁
   │
   ├─ 第一轮全不通 → 第二轮（tier 1，CDN 兜底）并发竞速
   │    fastly / cdn / gcore .jsdelivr.net ／ cdn.statically.io
   │
   ├─ parseManifest()：比 version 与 BuildConfig.VERSION_NAME
   │    ├─ 不比当前新 → UpToDate
   │    ├─ 有新版本   → Available(info)  → 弹窗展示 notes
   │    └─ 解析失败   → Failed(reason)   → 展示原因 + 「浏览器打开」兜底
   │
   └─ 用户点「下载并安装」
        ├─ 从命中线路开始**顺序**重试（APK 1.5MB，不做并发浪费流量）
        ├─ 下载到 cacheDir/updates/*.apk.part
        ├─ verifyApk()：PK 头 → 大小 → SHA-256
        ├─ 改名成正式文件
        └─ FileProvider + ACTION_VIEW 拉起系统安装器
```

### 6.3 多线路：为什么不猜、而是竞速

`raw.githubusercontent.com` 在国内基本整段不通。早期实现是「直连 → 镜像 A → 镜像 B」**顺序**重试，
问题在于：每条死线路都要等超时（6~8 秒），三条死线就是 20 秒的黑屏式等待；而且哪条能通因人因网而异。

现在改为**并发竞速**：同一轮的线路同时发请求，第一个返回合法清单的胜出，其余立刻取消。
用户不需要知道哪条线通，也不用 VPN。

| tier | 线路 | 为什么在这个位置 |
|---|---|---|
| 0 | `raw.githubusercontent.com` | 官方直连，海外最快 |
| 0 | `ghfast.top` | 路径前缀式加速，基本不缓存 |
| 0 | `gh-proxy.com` | 同上，备用 |
| 0 | `ghproxy.net` | 同上，备用 |
| 0 | `gh.llkk.cc` | 同上，备用 |
| 1 | `fastly.jsdelivr.net/gh/…` | CDN |
| 1 | `cdn.jsdelivr.net/gh/…` | CDN |
| 1 | `gcore.jsdelivr.net/gh/…` | CDN |
| 1 | `cdn.statically.io/gh/…` | CDN，**仅用于取清单** |

**为什么分两级**：CDN 会缓存分支上的文件（`jsDelivr` 对 `@branch` 的缓存可达数天）。
若第一轮就跑 CDN，一个过期的 `latest.json` 会让应用误报「已是最新」，用户永远收不到更新。
所以 tier 0（不缓存）先跑；只有它们全不通时才启用 tier 1，宁可慢一点也要保证"能更新"。

**APK 下载不受 tier 限制**：APK 位于 `vX.Y.Z/` 版本固定路径，内容不可变，CDN 缓存是安全的。
唯一的例外是 `Statically` 取 APK 会挂住不出字节（实测 25 秒 0 字节），因此标了 `manifestOnly`，不参与下载。

镜像只做**字节转发**、不改内容，且下载后仍有 SHA-256 兜底校验 —— 中间环节不老实也装不上。

> 加新线路前请先用 `curl -r 0-1023` 实测该域名下 `/<原始URL>` 真能拿到内容。
> 本文档记录的线路是**实测过**的；`github.moeyy.xyz`、`hub.gitmirror.com`、
> `ghproxy.cc`、`gh-proxy.net`、`gitdl.cn` 实测已死，不要加回来。

### 6.4 三级校验（从便宜到贵）

```kotlin
// ① APK 是 zip，头两字节必须是 "PK"；且不能小于 100KB（防代理返回错误页）
// ② 大小：优先用清单声明的字节数，否则用响应头 Content-Length
// ③ SHA-256：清单给了摘要就逐字节比
//    —— 这是唯一能发现"内容被中间环节替换"的检查，镜像越多越需要它
```

### 6.5 安装

Android 8.0+ 需要用户先授权「安装未知应用」：

```kotlin
canInstall(context)          // 查 PackageManager.canRequestPackageInstalls()
unknownSourcesIntent(context) // 没授权时跳到 ACTION_MANAGE_UNKNOWN_APP_SOURCES
install(context, apk)        // FileProvider.getUriForFile + ACTION_VIEW
```

> `clipData` 不是装饰：部分 ROM 的安装器只认 `clipData` 里的 grant，单靠 `FLAG_GRANT_READ_URI_PERMISSION` 会读不到文件，表现为"安装器一闪而过"。

### 6.6 需要的权限与清单声明

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.REQUEST_INSTALL_PACKAGES" />

<provider
    android:name="androidx.core.content.FileProvider"
    android:authorities="${applicationId}.fileprovider"
    android:exported="false"
    android:grantUriPermissions="true">
    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/file_paths" />
</provider>
```

`file_paths.xml`：

```xml
<paths>
    <cache-path name="updates" path="updates/" />
</paths>
```

### 6.7 隐私边界

全流程只在用户**主动点击「检查更新」**时发生。不上报任何设备信息，不访问除 GitHub 及其加速镜像之外的任何域名。

## 9. 发版后验证链（四步）

```bash
bash scripts/release.sh patch
```

1. **旧版本的文件里没有残留**
   ```bash
   grep -nE 'appVersion(Name|Code) = ' app/build.gradle.kts
   ```
2. **GitHub Actions 该次运行 success**（`release` job，不是只有 `verify`）
3. **公共仓库出现新版本目录**
   ```bash
   curl -fsSL "https://raw.githubusercontent.com/LuckyLearning/Release/main/GlucoNote/latest.json?nocache=$(date +%s)" | head -20
   # version 应为新版本号
   ```
4. **应用内「我的 → 版本更新 → 检查更新」能收到新版本**，下载后 SHA-256 校验通过、可正常安装

## 10. 常见故障对照

| 现象 | 根因 | 处理 |
|---|---|---|
| CI `Failed to find package 'tools'` | 用了失效的 `setup-android@v3` | 改成直接调 `sdkmanager` |
| `Plugin kotlin.plugin.compose not found` | 该插件只有 Kotlin 2.0+ 才有 | Kotlin 1.9 用 `buildFeatures.compose` + `composeOptions` |
| `Compose Compiler 1.5.15 requires Kotlin 1.9.25` | 编译器与 Kotlin 版本不匹配 | `kotlinCompilerExtensionVersion = "1.5.14"` |
| `Cannot access 'weight': it is internal` | 顶层 `weight` 不能 import | 在 `Row`/`Column` 的 scope 里调，跨函数传 `Modifier` 参数 |
| `Unresolved reference: OutlinedButtonDefaults` | material3 1.2.1 无此对象 | 边框直接用 `BorderStroke` |
| `Val cannot be reassigned` in `Paint().apply{}` | Composable 形参 `color` 遮蔽了属性 | 写 `this.color = …` |
| 发布后应用仍提示有新版本 | tag 与 `versionName` 不一致 | 闸门已拦；手动发版时务必同步两处 |
| `publish-release-repo.sh` 推送失败 | `Release` 仓库 `main` 开了分支保护 | 关掉保护 |
| `latest.json` 仍是旧版本 | CDN 缓存 | 脚本自带带 `nocache` 参数的重查循环 |

## 11. 与 WindTone 的对应关系

| 能力 | WindTone | GlucoNote |
|---|---|---|
| 版本文本 | `app/build.gradle.kts` 顶部 `appVersionName/Code` | 同 |
| 一键发版 | `scripts/release.sh` | 同（`--verify` 简化为 tag 实查） |
| 发布脚本 | `publish-release-repo.sh` + `gen-release-manifest.py` | 同（去掉 ABI 分包，单包） |
| 清单 | `<App>/latest.json` | 同（`assets` 只有一条） |
